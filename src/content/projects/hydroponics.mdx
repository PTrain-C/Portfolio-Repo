## What it is

A hydroponic system for the Food For Thought Foundation's Farms for Thought program. An Arduino UNO R4 WiFi reads pH and electrical conductivity (EC, which tracks how much nutrient is in the water), and when either drifts out of range it doses small amounts from four peristaltic pumps until it's back. I wrote all of the code.

## The control loop

Every 10 seconds it runs one dosing cycle. It uses deadband control, so it leaves the water alone while it's in range. The pH and EC loops are independent, so if one probe fails the other keeps regulating. EC goes first on purpose: adding nutrients moves the pH, so if pH were corrected first the EC step would just knock it back out. Locking in EC first means the pH loop isn't chasing a moving target.

## The bus

Every sensor and pump is an Atlas Scientific EZO module. All seven sit on one I2C bus:

| Device | Address | Job |
| --- | --- | --- |
| pH sensor | `0x63` | Reads pH, 815 ms per read |
| EC sensor | `0x64` | Reads EC, TDS, salinity, and specific gravity as CSV, 570 ms per read |
| Temperature | `0x66` | Initialized, but not part of the control loop |
| pH down pump | `0x67` | Doses acid |
| pH up pump | `0x68` | Doses base |
| EC up pump | `0x69` | Doses nutrient concentrate |
| EC down pump | `0x6A` | Doses water to dilute. Set to 0 to disable |

The pumps also had undocumented protocol limits that were getting my dose commands rejected. I isolated them and wrote them into the README: the pumps only accept a lowercase `d,<ml>` dose command over I2C (uppercase comes back as an error), and volumes can have at most two decimal places, so `d,0.20` works and `d,0.200` doesn't.

## Look at the bus first

I spent too long assuming the bugs were in my own logic. Readings were occasionally garbage, with no pattern. The vendor sample code read bytes until the EZO's end-of-data byte, `0x00`, but once a device has nothing left to send, the I2C bus itself hands back `0xFF`, and it was copying those into the buffer as data.
